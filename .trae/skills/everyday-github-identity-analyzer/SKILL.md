# GitHub 账号身份线索研判助手

这个 Skill 用于基于 **GitHub 账号公开可见的数据**，检索其所有公开仓库、贡献者、关联主页与外链，筛选出更像**个人项目**的仓库，并综合研判与该账号**高相关**的身份线索与公开来源。

它适用于用户希望从一个 GitHub 主页出发，寻找账号主人可能使用过的中文名、别名、GitLab 账号、公开个人主页等身份线索，但**不适用于捏造身份或输出无证据的猜测**。

## 触发场景

当用户明确提出以下意图时调用：

- 提供一个 GitHub 账号链接，要求分析该账号相关的个人信息线索。
- 要求从 GitHub 公开仓库里找出更像个人项目的仓库，并据此识别作者身份。
- 要求寻找账号可能使用过的中文名、GitLab 账号、别名、个人主页或其他公开身份线索。
- 要求排除无关贡献者、朋友协作者、组织项目噪音后，再给出更可靠的个人信息判断。

典型表达示例：

- 给你一个 GitHub 主页，帮我从公开仓库里判断这个人可能的中文名
- 分析这个 GitHub 账号的个人项目，找找有没有关联的 GitLab 身份
- 请排除 fork 和多人协作仓库，只保留能说明账号主人身份的线索

## 必要信息

执行前，必须从用户输入中明确拿到以下字段：

- GitHub 账号链接

如果用户没有明确提供 GitHub 账号链接，**不要自行猜测账号**，必须先追问。例如：

- 请提供要分析的 GitHub 账号主页链接
- 你要我分析的是哪个 GitHub 用户主页？

## 执行原则

1. 仅使用**公开可访问**的数据源，不尝试获取私有仓库、私有邮件、令牌或受限信息。
2. 必须先检索该账号的**全部公开仓库**，再从中筛选更像个人项目的仓库，不能只看单个仓库就下结论。
3. “个人项目仓库”优先满足以下特征：
   - 仓库不是 fork
   - 仓库 owner 就是目标账号本人
   - 贡献者少于 10 人
   - 仓库不是明显的组织协作仓库、镜像仓库、课程作业汇总仓库或热门第三方项目镜像
4. 线索研判时必须优先关注**高相关证据**：
   - 仓库主页、README、自述、个人站点、社交链接
   - 仓库贡献者名称与账号本人在多个个人项目中的重复出现
   - GitLab 仓库链接、GitLab 用户名、跨平台同名账号
   - Git 提交作者名、公开 profile name、公开 bio、blog、homepage 等自填信息
5. 必须排除明显无关内容，例如：
   - 仅在单个仓库短暂参与的朋友或路人贡献者
   - 组织成员、大型项目维护者、机器人账号、依赖同步账号
   - 与目标账号没有重复关联、没有公开身份交叉证据的中文名贡献者
6. 不能把“疑似”当作“确定”。所有结论必须标明**置信度**与**来源**，并明确哪些只是低置信度线索。
7. 输出时仅给出**公开且与身份研判直接相关**的信息，例如可能姓名、别名、公开主页、GitLab 账号、公开自我介绍。不输出与任务无关的敏感信息，也不夸大推断。

## 标准执行流程

### 1. 参数确认

从用户请求中提取并复述以下变量：

- `<github_profile_url>`
- `<github_username>`

若无法从链接中稳定解析出用户名，停止执行并向用户追问。

### 2. 账号有效性检查

先确认该链接对应的是一个真实存在的 GitHub 用户主页，而不是仓库页、组织页、gist 页或无效链接。

检查要点：

- 能否成功打开用户主页
- 用户名是否可解析
- 主页是否公开可访问
- 如果是组织账号而非个人账号，要明确告知用户结果可能噪音更高

如果账号不存在或无法访问，直接告知用户无法执行。

### 3. 拉取全部公开仓库

必须收集该账号的**全部公开仓库**，必要时处理分页。

优先收集的仓库字段包括：

- 仓库名
- owner
- 是否 fork
- 是否 archived
- description
- topics
- homepage
- 默认分支
- stars / forks
- 创建时间 / 最近更新时间
- 语言分布

如果工具允许，优先使用 GitHub 公开 API；若 API 不可用或受限，再退回读取公开网页。

### 4. 识别“个人项目仓库”

对全部公开仓库进行筛选，优先保留：

- 非 fork 仓库
- owner 为目标账号本人
- 贡献者数量小于 10
- README、description、homepage 中带有明确个人表达、实验项目、博客、作品集、脚本、工具集特征

应降低权重或排除的仓库包括：

- fork 仓库
- 明显组织仓库或公司项目
- 贡献者很多的协作项目
- 自动镜像、模板、课程汇总、题库同步、纯收集类仓库

必要时为每个仓库打一个“个人项目相关性”标签，例如：

- 高相关：很像本人长期维护的个人项目
- 中相关：可能是个人项目，但噪音较多
- 低相关：不适合作为身份判断依据

### 5. 收集身份线索

针对高相关和中相关仓库，继续收集以下线索：

- 仓库贡献者列表与贡献次数
- 贡献者用户名、公开名称、主页链接
- README、自述、项目文档中的署名、自我介绍、联系入口
- 仓库 homepage、docs、issue 模板、发布页里出现的个人站点或社交链接
- 指向 GitLab 的仓库链接、镜像链接、个人主页链接
- 提交作者名中反复出现的人名、拼音名、中文名、英文别名

重点寻找两类信号：

- **疑似中文名**：贡献者 display name、提交作者名、README 署名中出现中文姓名，或稳定出现的拼音式全名
- **疑似 GitLab 关联**：README、homepage、镜像说明、个人主页中出现 GitLab 用户页、GitLab 仓库页、同名账号跳转

### 6. 交叉验证与排除噪音

综合判断时，必须区分“账号本人线索”与“他人贡献者线索”。

优先判定为高相关的情况：

- 同一个姓名或别名在多个个人项目仓库中重复出现
- GitHub profile name、提交作者名、README 署名、个人站点署名彼此一致
- GitHub 账号、个人主页、GitLab 主页上出现相同用户名或相同署名
- 某个中文名或别名既是主要贡献者，又与目标账号的主页/站点/项目文档发生交叉印证

应排除或降权的情况：

- 只有单个仓库出现一次的中文名，且该人只是次要贡献者
- 贡献者明显是朋友、同事、开源协作者、外部 PR 提交者
- 名称只在 issue、感谢名单、第三方引用中出现
- GitLab 链接属于依赖项目、上游项目、示例项目，而不是目标账号本人

如果证据不足，必须明确写“无法可靠判断”，不要为了给出答案而硬推断。

### 7. 结果输出

最终回复用户时，必须包含以下信息：

- 分析目标：`<github_profile_url>`
- 检索到的公开仓库总数
- 被判定为高相关/中相关/低相关的仓库数量
- 主要线索列表
- 每条线索的来源
- 每条线索的置信度：高 / 中 / 低
- 明确排除掉的典型噪音类型
- 最终给出的“可能个人信息结果”

## 常用 API 与技巧

### 推荐优先使用的公开 API

优先使用 GitHub 公开 API 拉结构化数据；如果 API 不可用、返回不完整，或需要补充页面展示信息，再退回抓取公开网页。

- 用户主页信息：`https://api.github.com/users/<github_username>`
  - 用于读取 `name`、`bio`、`blog`、`twitter_username`、`public_repos` 等公开字段
- 全部公开仓库：`https://api.github.com/users/<github_username>/repos?per_page=100&sort=updated`
  - 用于获取仓库总表，并按 `fork`、`homepage`、`description`、`language`、`updated_at` 初筛
- 仓库贡献者：`https://api.github.com/repos/<owner>/<repo>/contributors?per_page=10`
  - 用于判断仓库是否多人协作、是否有机器人账号、目标用户是否为主要贡献者
- 仓库 README：`https://api.github.com/repos/<owner>/<repo>/readme`
  - 建议配合 `Accept: application/vnd.github.raw+json` 获取原始文本，便于查找署名、主页、GitLab、联系方式
- 最近提交：`https://api.github.com/repos/<owner>/<repo>/commits?per_page=5`
  - 用于提取 `commit.author.name`、`commit.author.email`、`author.login`，识别稳定重复的作者名或别名

### 网页兜底与补充抓取

- GitHub 用户页：`https://github.com/<github_username>`
  - 当需要确认 profile 展示名、热门仓库、贡献概览、公开页面文案时使用
- 仓库主页站点：优先抓取仓库的 `homepage` 字段指向的站点
  - 用于寻找项目署名、站点标题、页脚信息、外链入口
- GitHub Pages 或 Demo 站点
  - 有时会出现比 README 更直接的署名或项目归属信息

### 实操技巧

- 先总表后深挖：必须先拿全量仓库列表，再筛个人项目，避免只看单个仓库就下结论
- 先排 fork：fork 仓库默认降权，除非其中存在明确且重复出现的本人提交作者名
- 看重复出现：同一个名字、别名、邮箱前缀、站点署名若在多个高相关仓库重复出现，置信度明显更高
- 看字段交叉：优先交叉验证 `profile name`、README 署名、提交作者名、站点署名、homepage 外链
- 区分 Git 作者与 GitHub 作者：`commit.author.name` 可能是历史本地 Git 身份，`author.login` 才是 GitHub 关联账号；两者不一致时要分别记录
- 识别噪音账号：机器人、dependabot、一次性协作者、组织成员、大型项目贡献者默认排除
- 搜索引擎补充验证：可用搜索引擎检索用户名、提交作者名、邮箱前缀、站点域名，寻找公开主页或跨平台同名账号
- 只输出必要结果：如果只能得到弱线索，应明确标为低置信度，不要把用户名直接扩写成实名
- 保留排除理由：最终输出不仅要写“保留了什么”，也要写“为什么排除其他名字或仓库”

## 判定标准

可纳入最终结果的高质量线索通常满足以下任一条件：

- 在两个及以上高相关个人项目中重复出现
- 与 GitHub 主页自填信息互相印证
- 与 GitLab 主页、个人站点、README 署名形成交叉验证
- 是目标账号本人最主要的提交作者名或 profile name

仅可作为低置信度线索、不能当成最终结论的情况：

- 只出现一次的中文名
- 只来自某个次要贡献者的名字
- 只在第三方链接、引用、感谢名单中出现的名字
- 只凭用户名拼测真实姓名，缺乏公开证据支撑

## 失败处理

出现以下任一情况时，不要假装完成，必须如实说明：

- 用户未提供明确的 GitHub 账号链接
- GitHub 账号不存在、无法访问，或无法稳定识别用户名
- 未能取得该账号的公开仓库列表
- 没有找到足够的个人项目仓库，无法形成可靠研判
- 找到的线索大多来自外部贡献者，无法区分是否为账号本人
- 所有候选信息都缺乏交叉证据，无法给出可信结果

## 额外要求

- 不要把组织项目中的多人贡献者直接当作目标账号的个人身份。
- 不要因为贡献者名字是中文就直接认定其为账号本人。
- 不要将 fork 仓库、镜像仓库或大型协作仓库作为主要判断依据。
- 不要把低置信度猜测写成确定事实。
- 不要省略来源说明。
- 不要省略排除理由。
- 如果最终只能得到弱线索，也要如实标注为“弱相关”或“低置信度”。
